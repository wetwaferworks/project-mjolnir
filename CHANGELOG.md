# Changelog

## Unreleased

- Documentation: the README and guide rewritten to the current tree, for people first. The named stages remain M0 and M1; work after M1 (the C and CUDA port, the hemispheres, the hardened ledger) is described as Unreleased, which is how this changelog lists it. The next named stage on the roadmap is still M2. There is no M3, M4 or M5 in this repository.
- The Python ledger takes the same writer token as C. `ledger.append` creates `<ledger>.writer` exclusively in the C format (with the process start stamp the C side uses to tell a live writer from a dead one), refuses at once when anyone holds it, cuts off its own bytes if the append fails, and gives the token back. Before this, Python appends ignored the token and could interleave with a C writer. Tests include C reporting a live Python writer as running and refusing to clear it.
- On Windows, folder listings skip symbolic links and junctions, as they already did on Linux, so a link dropped into a working folder cannot point a listing at a file elsewhere. Readers of the ledger and other files now let a writer keep appending while they read.
- Apply and rollback check the original before restoring from it. The original model file is hashed in full through the very handle the restore reads from and compared with the base record; if it changed after register (a disk error or a stray write), the apply is refused before the dirty marker or any byte is written, and nothing is journaled, so "base" can never be rebuilt from a changed source. Both model files are also checked again on their open handles (same file as checked by name, working file not the original and not hard-linked), closing the gap between the check and the open. This costs one full read of the original per apply. Tested by flipping one byte of the original after register.
- The dream ledger takes one writer at a time. Every append first creates `<ledger>.writer` exclusively and removes it when done; a second writer is refused (`busy-another-writer`) with a line naming the process, host and start time that holds it, and never waits or takes the token over. A token left by a run that died is cleared only with `mj_ledger_verify --release-stale`, and only when that process is provably not running on this host (a reused process id counts as gone; another host or an unreadable token is refused). The cleared token is kept as `.writer.stale-<when>-<id>`. A failed append now cuts off the bytes it wrote, so it cannot leave a torn line. `mj_ledger_verify --repair-tail` removes a torn last line only after every complete record verifies and a full backup (`.torn-<when>.bak`) is written; it refuses when a complete record is wrong and never edits history. `mj_ledger_verify --expect SEQ:HEX` checks a head written down earlier, so removing or rewriting records is caught. Tests for two writers, many writers in threads and processes, stale and foreign tokens, torn lines, tamper and repair; the ledger fuzz target also covers the torn-tail check and the token parser.
- The left and right hemispheres on toy policies (`mj_hemi`, `mj_classroom`, the `mj_hemi` tool), as a two-stage pipeline. Stage 1, the classroom: the left acts, the right watches and grades, the actor learns from its errors and the watcher from its misses, each kept only if better on holdout worlds. Stage 2, the hemisphere swap: each side plays while the other watches, both sample sets combine into one child, kept only if it beats both parents. The answer key is the final judge throughout, every change is on a copy with SHA-checked rollback, and every lesson and round is journaled. The MJHEMI2 sample-set format (full SHA-256 of the model that acted and the one that watched, and whether the set is a lesson or holdout evidence) with a fuzz target, a CUDA holdout scorer that matches the CPU bit for bit, and the [hemispheres page](docs/hemispheres.md).
- `mj_hemi gate` and `mj_hemi_gate`: the keep-or-roll-back decision for real models. A world outside Mjolnir (PCHIE) plays and grades the rounds and writes lesson and holdout sample sets; it passes no scores. Mjolnir works out every score itself from the holdout sets and decides only when the sets are bound by SHA-256 to the parent, the candidate and (for a swap) the second parent, cover the very same held-out states, record moves that match their recorded distributions, and agree on every grade the answer key gave. Anything else is refused with the reason (exit 2) and nothing is journaled. Exit 0 keeps, 3 rolls back. Tested in `test_hemi` and by the hemisphere fuzz target.
- The real-weight path in C: a safetensors header reader that checks every offset, size and shape against the file before trusting it; MJDELTA1 pack and unpack, byte for byte as Python writes them; the apply on the CPU or, with `-DMJ_CUDA=ON`, the GPU, giving the same bytes either way; the working copy, its state file and checkout; register and apply with the same ledger records; and the `mj_real` tool. Parity tests against Python in `py_c_port`. See [docs/C-PORT.md](docs/C-PORT.md).
- The C apply writes a dirty marker (`MJOLNIR-DIRTY.txt`) before changing the working model file in place and removes it once the writes are read back, so a cut-short write is reported and repaired by the next apply.
- C register refuses a working folder that is the original folder (or inside it, or around it) before anything else; the Python register only checked this when it had to copy.
- Atomic writes in C use a temporary name of their own (`<path>.<pid>.<n>.tmp`, created exclusively), so two writers never share or delete each other's temporary file.
- Fuzz targets for the safetensors header and MJDELTA1 parsers.
- Replays, grades and the toy nap in C (`mj_replay`, `mj_grades`, `mj_toytrain`, the `mj_m1` tool), with a small JSON reader that follows Python's rules. The same run folders give byte-identical replay dumps; grades and toy-nap ledgers are shared both ways. Parity tests in `py_c_port_m1`; a JSON fuzz target.
- The labeling page in C (`mj_labeler`, `mj_m1 label`): the same page, order of steps, answers and grades ledger as the Python tool, on 127.0.0.1 only. Stalled connections are dropped after 5 seconds and the port is bound exclusively on Windows. Side-by-side parity test against the Python session; an HTTP fuzz target.
- The low-rank edit in C (`mj_lowrank`, `mj_real lowrank`): whitening by the background keys, QR, SVD and truncation in double, with cuBLAS for the big products when built with CUDA. Matches Python's `low_rank` to a few parts in a million.

- Documentation: a guide under `docs/guide/` (overview, architecture, getting started on Windows and Linux, build and test, design principles, intended use and safety, labeling, real-weight edits, glossary), a roadmap, a README in every source folder, and `AGENTS.md`, `CREDITS.md`, `CONTRIBUTING.md`, `SECURITY.md` and `PROVENANCE.md`.

## M1

- Labeling tool, read-only real replays with partial-credit labels, GPU training of the toy policy, and the real-weight edit path on a working copy (register, dream, apply, evaluate, verify).
- `mj_store_verify`, a read-only checker for any version store.
- Model access note: API keys in Windows Credential Manager, no OAuth.

## M0

- Weight version store, hash-chained dream ledger and verifier, partial-credit scorer, reward-weighted update rule with step cap and drift gates, dry-run nightly and nap drivers, and a CMake test bench with fuzzers.
