# Stage M1: grading, real replays, GPU training, and the real-weight edit path

M1 builds on the M0 foundations. The C library stays the reference for every
file format, and the new Python side reads and writes exactly the same formats.
The test bench checks that the C tools accept what Python writes, and the
other way round.

Everything M1 produces (stores, ledgers, grades, reports) goes into a data
folder you name with `--data`. Keep that folder outside any shared or published
folder, because it holds run data. Nothing in this repository ever holds
weights, run data or a ledger.

## Setting up

Python 3.11 or newer. The labeling tool, replays, stores and ledgers need
nothing beyond the standard library. GPU training and the real-weight path
need `torch` (a CUDA build for the GPU) and `numpy`; the real-weight path also
needs `transformers` and `safetensors`-compatible model files.

Run commands from the `python` folder, or put it on `PYTHONPATH`:

```
python -m mjolnir replays --runs RUN_FOLDER
```

## 1. The labeling tool

```
python -m mjolnir label --runs RUN_FOLDER [RUN_FOLDER ...] --data DATA_FOLDER
```

This opens a page on this machine only, at `http://127.0.0.1:8765/`. It shows
one step of a recorded run at a time: where the agent stood, what was open,
what it proposed, what it chose and what happened, a small map of its path,
and the label the automatic grader suggests. The least certain steps come
first: the ones where the top two proposals were closest, and loops and
rewards before plain forward steps.

It is built for voice and for as little typing as possible:

| Key | Button | Meaning |
|---|---|---|
| Enter | Agree | take the suggested label |
| 1 or G | Good | a good step |
| 2 or B | Bad | not productive, not yet |
| 3 or P | Productive | it moved the task forward |
| Space or S | Skip | come back to it later |
| Backspace | Back | the previous step; grading it again adds a newer grade |

The buttons are large and named, so Windows Voice Access can press them by
saying "click Good", "click Agree" and so on.

Each grade is one line in its own hash-chained ledger, `grades.mjl`, in the
same MJL1 format as the dream ledger (outcome `grade`, the grader's name, the
step, and the label). Grades are never edited: a newer grade for the same step
comes later in the chain and wins. The page only answers requests from this
machine that carry its own marker, so another web page cannot post grades.
The server runs on one thread, so requests are handled one after another and
nothing needs a lock.

## 2. Real replays

PCHIE research logs (format `pchie.research.v1`) are hash-chained JSON lines.
`mjolnir.replay` opens them for reading only, checks every line's hash and its
link to the line before, and refuses a log with any break. A run copied to two
places is counted once. Each step gets an automatic partial-credit label, as in
design principle 8:

- **productive**: the step earned a reward (the key or the goal)
- **good**: the step reached ground the run had not stood on before
- **not yet**: the step went back to ground already visited

## 3. Training the toy model on the GPU

```
python -m mjolnir toy-seed --data DATA_FOLDER
python -m mjolnir toy-nap --runs RUN_FOLDER --data DATA_FOLDER [--integrate]
```

A nap on the M0 toy policy, now fed by real replays. Every fourth run is held
out as the golden set (older memories). The dream batch uses JD's grade where
he gave one and the automatic label otherwise, with the golden steps mixed in
after the new ones (design principle 5). Training runs on the GPU: it raises the
likelihood of productive actions and lowers the likelihood of unproductive
ones (design principle 3), and clamps every weight to the step cap after every step
(design principle 4). The result is rounded to the Q16 format, so `mj_nap` and
`mj_nightly` can load it, and goes through the four M0 gates: step cap,
behavior shift on the golden set, golden score not lower, task score higher.
The candidate is always saved; the live version only moves with `--integrate`
and when every gate passes. Every nap writes one line to `toy-dreams.mjl`.

The toy model is tiny (eight inputs, four actions), so the GPU part takes a
second or two. It is there to prove the loop end to end on real material.

## 4. The real-weight edit path

The path works on a working copy of a model, never on the original download.

```
python -m mjolnir real-register --original ORIGINAL --working WORKING --data DATA_FOLDER
python -m mjolnir real-dream    --working WORKING --data DATA_FOLDER --runs RUN_FOLDER
python -m mjolnir real-apply    --original ORIGINAL --working WORKING --data DATA_FOLDER --version ID
python -m mjolnir real-eval     --original ORIGINAL --working WORKING --data DATA_FOLDER --runs RUN_FOLDER
```

The register, apply and verify steps also run in C, with no model code,
through `mj_real` (see [the C port](C-PORT.md)); both write the same store,
ledger and state files, so either can pick up where the other left off:

```
mj_real register --original ORIGINAL --working WORKING --data DATA_FOLDER
mj_real apply    --original ORIGINAL --working WORKING --data DATA_FOLDER --version ID [--cpu]
mj_real verify   --dir DIR --sums FILE
mj_real status   --working WORKING
```

**Register.** Checksums every file of the original, copies it to the working
folder, checks the copy byte for byte, and marks the original files
read-only. A base record (MJBASE1: each file's name, size and SHA-256) goes
into the real-weight store as a pinned milestone. The working folder must be a
separate folder and its model file must not be a hard link to the original.

**Dream.** Builds maze-step prompts from the replays (the four moves are
offered as letters A to D) and works out an edit to the MLP output projection
of chosen layers. The method is a first-order, low-rank form of rank-one model
editing (ROME, Meng et al. 2022), reward-weighted: for each example, the input
to the projection, its output, and the gradient of the reward-weighted answer
likelihood give one rank-one direction; the sum is truncated to a small rank.
As in ROME, each input is whitened by the covariance of the projection's inputs
over ordinary text (the golden set, the other prompt positions, and the part
every prompt's last position shares), so the edit follows what differs between
maze steps and stays quiet elsewhere.

The dream tries several strengths **in memory only**, as an overlay on the
forward pass, and scores each one on the examples it learned from, on held-out
runs, and on a golden set of general text. A strength passes only if every
gate holds:

- golden set: KL divergence from the unedited model at most 0.02 per token,
  loss at most 2% higher, top-1 agreement at least 97%
- task: the score rises on the examples it learned from and does not fall on
  held-out runs
- neither half pays for the other: good steps keep their accuracy and
  likelihood (on held-out runs too), and the chance of repeating a loop does
  not rise

It keeps the strongest passing strength and stores it as a candidate: an
MJDELTA1 file holding the low-rank factors, a few megabytes at most. Nothing is
written to the working copy at this step. When no strength passes, the dream is
recorded as rejected and nothing is stored.

**Apply.** Restores every tensor an earlier edit touched to the original
bytes, adds the version's chain of deltas oldest first, and writes only those
tensors back into the working copy, then reads them back. Applying `base`
rolls the working copy back to a byte-for-byte copy of the original.

**Evaluate.** Scores the original and the working copy as they are on disk,
so the measured effect includes the rounding to the model's 16-bit format.

**Running with 4 GB of graphics memory.** The model's weights stay in the
file and are mapped read-only, so loading can never change a file and the
operating system pages in only what is used. The two big embedding tables are
read row by row on the processor. Each decoder layer is copied to the GPU just
before it runs and dropped after; the layers an edit needs gradients through,
the output head and the small parts stay on the GPU. On a 4 GB laptop GPU one
pass over a batch of short prompts takes a few seconds, and a whole dream with
four trial strengths takes about a minute and a half.

## Standing rules this stage keeps

- The original download is never written, only read and checksummed.
- Every edit is a version in the store and a line in the ledger.
- An edited model is not wired into PCHIE's official runners, chat, or any
  official record, and lessons are not injected into prompts.
- Run logs are read-only.

## File formats added in M1

**MJDELTA1** (a stored real-weight edit):

```
MJDELTA1
base=<SHA-256 of the original model file>
count=<entries>
tensor=<name> rows=<r> cols=<c> rank=<k> scale=<float>    (one line per entry)
end
<per entry: U as r x k float32, then V as k x c float32, little-endian>
<SHA-256 of every byte above, 32 bytes>
```

The change to a tensor is `scale * U @ V`.

**MJBASE1** (the base record): the line `MJBASE1`, then one line per file:
`<sha256>  <size>  <name>`.

**MJWORK1** (the working copy's state, `MJOLNIR-STATE.txt` in the working
folder): `MJWORK1`, `applied=<version>`, then `touched=<tensor>` per tensor
that differs from the original.

**MJDIRTY1** (written by the C apply only, `MJOLNIR-DIRTY.txt` in the
working folder): the same layout as MJWORK1 with the first line `MJDIRTY1`;
`applied=` names the version the working copy held before, and the
`touched=` lines name every tensor about to be written. It is written before
the first byte of the model file changes and removed after the writes are
read back and the state file is updated. If it is still there, a write was cut
short: `mj_real status` reports the working copy as dirty, and the next apply
(of any version, or `base`) restores the named tensors too. The Python apply
does not write or read it.
